# 图片识别路由器 v2.1.0 与随手账 v0.3.0 协同升级设计

日期：2026-08-05

状态：已获用户设计确认

主项目：`image-intake-router`

协同项目：`personal-expense-ledger`

## 1. 背景与问题

真实订单图片测试暴露了五类系统性问题：

1. 图片没有经过可证明的视觉处理，附件携带的描述文本却被当成 `user_text`，造成“没有看到图片”与“金额、商品已确定”同时出现。
2. 当前统一事实仅覆盖商品名称、数量、规格和状态，无法表达标称重量、实际重量、计价重量、重量误差、单项实付、退款和未展开商品。
3. 当前费用投影只有最多 1000 字的 `note`，随手账数据库没有商品明细表，完整商品信息无法结构化保存。
4. 现有确认状态机把业务变化与适配器技术修正混为一谈，导致 `expires_at`、`piece` 等内部字段修正反复要求用户确认。
5. 默认回复被固定为详细双预览，暴露证据枚举、内部单位、ISO 时间、修订状态和调用信息，超出普通用户需要。

本次升级不是为某一张图片增加特殊规则，而是修复视觉入口、统一事实、费用存储、确认语义和用户输出之间的数据链路。

## 2. 目标

### 2.1 必须实现

- 每批图片只执行一次视觉识别，两个下游只读取同一份统一事实。
- 图片业务字段必须以成功的视觉执行为前提；识别未执行或失败时禁止预览和写入。
- 附件描述与用户正文严格分离，附件描述不能冒充 `user_text` 或 `visible_label`。
- 完整保留商品重量、数量、规格、单项金额、退款及图片完整性。
- 随手账仍保持“一单一笔”，同时以结构化行项目保存完整商品明细。
- 用户只确认业务内容一次；适配器内部规范化不触发二次确认。
- 默认回复压缩为一至两句，详细证据按需展开。
- 已成功写入的域或商品不得因其他域修正、失败或重复确认而重放。

### 2.2 非目标

- 本轮不修改食序管家核心程序、数据库或公开工具实现。
- 不在路由器中自建 OCR 或视觉模型服务。
- 不保存原图、附件路径、base64 或完整 OCR 文本。
- 不把退款自动写成收入、负支出或新的账目；退款只作为订单事实和商品明细保存。
- 不猜测图片中“还有 N 种商品”所代表的名称、数量或价格。
- 不实现随手账与食序管家的跨数据库原子事务。
- 不合并或改写随手账尚未发布的 `codex/v0.2.2-batch-delete` 分支。

## 3. 版本与兼容策略

### 3.1 图片识别路由器

- 产品版本升级为 `2.1.0`。
- 新增严格协议 `image-intake-router.v2.1` 和对应 Schema 文件。
- 保留 v2.0.1 发布和历史资产，不覆盖、不重写已有标签。
- v2.1.0 Skill 只生成 v2.1 统一事实，不在同一执行中回退到旧 v2 协议。

### 3.2 随手账

- 产品版本升级为 `0.3.0`。
- 从官方 `main` 基线开发；该基线包含公开 v0.2.1，不吸收未合并的 v0.2.2 批量删除功能。
- `expense_entry.create` 新增可选 `line_items`；不传该字段的旧文本记账继续工作。
- 数据库升级前沿用现有自动备份和迁移事务，失败时保留原数据库及备份。

### 3.3 食序管家

- 路由器按已安装食序管家的公开 Schema 生成适配载荷。
- 当前核对基线为产品版本 0.7.4.2；本轮不修改该仓库。
- 适配器负责把展示单位转换为工具单位，例如 `粒` 转为 `piece`，但统一事实保留原始展示语义。

## 4. 总体架构

```text
图片附件批次
    ↓
OpenClaw 图片媒体理解或原生视觉输入
    ↓
recognition_run 视觉执行记录
    ├─ 未执行/失败 → 停止，不生成业务预览，不写入
    └─ 成功/部分成功
            ↓
    image-intake-router.v2.1 统一事实
            ↓
    业务摘要 + business_digest
            ↓
        用户确认一次
            ↓
    ┌───────────────┴───────────────┐
随手账适配器                   食序管家适配器
    ↓                               ↓
账目 + 商品行项目              单位/可选字段内部规范化
```

视觉识别发生在事实形成之前。任何投影、摘要和适配器都不得重新读取原图。

## 5. 视觉执行门禁

### 5.1 `recognition_run`

统一事实顶层新增必填对象：

```json
{
  "recognition_run": {
    "status": "succeeded",
    "method": "media_understanding",
    "attachment_count": 2,
    "processed_attachment_count": 2,
    "attachments": [
      {
        "attachment_id": "image-1",
        "status": "succeeded",
        "content_complete": false,
        "limitations": ["bottom_rows_collapsed"]
      }
    ],
    "issues": []
  }
}
```

允许状态：

- `succeeded`：所有选中图片均得到视觉结果。
- `partial`：至少一张图片得到视觉结果，同时存在模糊、裁切、遮挡或单张处理失败。
- `failed`：视觉调用已发生但无可用事实。
- `not_executed`：没有可用视觉入口，或只收到附件描述/占位文本。

只有 `succeeded` 或 `partial` 可以产生图片事实。`partial` 必须把不完整范围写入订单质量字段，并禁止根据缺失区域补全。

### 5.2 来源隔离

证据来源调整为：

- `visible_label`：来自成功视觉执行中可定位的图片文字或视觉事实。
- `user_text`：用户在消息正文中亲自陈述的事实。
- `calculated`：只由已有事实确定性计算而来。
- `reference_database`：经规则允许的通用参考数据。
- `visual_estimate`：明确允许的视觉区间估计。

附件抽取文本、文件描述、平台生成的图片摘要或占位符统一记为 `attachment_context`。它是非业务证据，不能填充金额、商品、重量、状态或时间字段。

每个已知字段必须记录：

- `source`
- `confidence`，范围 0 到 1
- `calculated`
- `attachment_id` 或用户正文定位
- `location`
- 必要时的 `reason`

视觉失败时不得把附件描述降级成 `user_text` 继续执行。

### 5.3 多图处理

- OpenClaw 图片附件策略配置为处理本批全部图片，而不是默认只处理第一张。
- 每张图片只进入视觉能力一次。
- 跨图去重只在订单标识、相邻行、规格、价格和重叠顺序等身份线索一致时执行。
- 同名不同规格不得合并。

## 6. 统一事实模型

### 6.1 通用字段包装

文本、数量、金额、日期和布尔事实使用同一种字段包装：

```json
{
  "value": 11.78,
  "unit": "CNY",
  "confidence": 0.99,
  "calculated": false,
  "evidence": [
    {
      "source": "visible_label",
      "attachment_id": "image-1",
      "location": "商品行右侧实付"
    }
  ]
}
```

未知值使用 `null` 和对应问题说明，不得用 0、空字符串或通用默认值伪装已知事实。

### 6.2 商品事实

每个商品至少包含：

- `full_name`
- `normalized_name`
- `specification`
- `purchase_quantity`
- `quantity_unit`
- `nominal_weight_or_volume`
- `actual_weight_or_volume`
- `billing_weight`
- `weight_variance`
- `original_amount`
- `unit_price`
- `line_paid_amount`
- `refund_amount`
- `production_date`
- `line_status`
- `item_type`
- `visibility_status`

重量或容量使用数值与单位组合，原始规格文字同时保留。例如榴莲应表达为：

- 规格：约 2.1 kg
- 数量：1
- 数量单位：粒或件的展示语义
- 单项实付：119.00 CNY
- 重量误差：228 g
- 自动退款：12.92 CNY

不能因为下游库存接口使用 `piece` 而丢弃 2.1 kg 规格。

### 6.3 订单事实

订单至少包含：

- `merchant`
- `transaction_time`
- `order_status`
- `goods_subtotal`
- `activity_discount`
- `coupon_discount`
- `packaging_fee`
- `delivery_fee`
- `final_paid_amount`
- `refund_total`
- `declared_item_kind_count`
- `recognized_item_kind_count`
- `hidden_item_kind_count`
- `has_unexpanded_items`
- `content_complete`

当图片显示“还有 2 种商品”且可见 7 种时：

- `declared_item_kind_count = 9`
- `recognized_item_kind_count = 7`
- `hidden_item_kind_count = 2`
- `has_unexpanded_items = true`
- `content_complete = false`

隐藏商品只作为订单完整性事实存在，不创建占位商品行，也不进入下游。

## 7. 投影设计

### 7.1 随手账投影

费用投影保留订单级字段，并新增：

- `line_items`：所有可识别实际购买商品的结构化明细。
- `note`：适合账单列表展示的压缩摘要。
- `detail_completeness`：完整、部分或不可用。
- `omitted_item_count`：图片未展开或无法识别的商品种类数。

退款事实进入 `line_items.refund_amount` 和订单事实，但不改变 `final_paid_amount`，除非图片明确表明最终实付已经扣除退款且该关系可确定。

当商品很多时，`note` 只展示前若干项和“其余 N 种商品略”；数据库 `line_items` 仍保存所有可见明细。

### 7.2 食序管家投影

- 只投影明确属于食品且具备已购买并已收到证据的商品。
- 原始事实与技术载荷分离：原始单位保留，适配器把 `粒`、`件` 转成 `piece`。
- 标称重量、包数与每包容量优先映射到 `package_count`、`quantity_per_package`、`package_unit`、展示数量字段。
- 有效期未知时按已安装工具 Schema 生成允许的未知表达；该表达属于适配器细节，不进入用户确认摘要。
- 图片未展开商品不入库。

## 8. 随手账数据库与接口

### 8.1 新表

新增 `expense_line_items`，至少包含：

- `id`
- `expense_id`
- `ordinal`
- `full_name`
- `normalized_name`
- `specification`
- `quantity_value`
- `quantity_unit`
- 标称、实际、计价重量或容量的值与单位
- `weight_variance_value` 与单位
- `original_amount_minor`
- `unit_price_minor`
- `paid_amount_minor`
- `refund_amount_minor`
- `production_date`
- `line_status`
- `fact_snapshot_json`

`expense_id` 外键指向 `expenses`。删除或撤销账目时，行项目遵循账目的状态和可恢复语义，不形成孤儿记录。

### 8.2 创建事务

`expense_entry.create` 接收可选 `line_items`：

1. 校验整笔账及所有行项目。
2. 在同一 SQLite 事务中写入账目和行项目。
3. 任一行项目失败则整笔回滚。
4. 现有稳定幂等键覆盖整笔账和行项目集合。
5. 同一幂等键、相同请求返回原结果；相同幂等键、不同明细返回冲突。

### 8.3 查询与导出

- `expense_entry.search` 和最近账目响应默认返回商品摘要，可按接口约定请求完整行项目。
- CSV 导出至少保留订单级账目行为；是否另附商品明细 CSV 由实施计划中的兼容性测试决定，但不得静默丢失数据库明细。
- 报表汇总仍以 `expenses.final_paid_amount` 为准，不把商品行金额再次求和计入支出。

## 9. 一次确认语义

### 9.1 业务摘要与摘要指纹

预览生成 `business_digest`，覆盖：

- 实付金额和分类
- 商家与业务时间
- 商品名称、数量、规格和单项实付
- 退款事实
- 记账/入库范围
- 图片完整性警告

用户确认的是该业务摘要，而不是下游技术载荷。

以下变化必须生成新预览并重新确认：

- 金额、商品名称、数量、规格或单项价格变化
- 新增或移除商品
- 退款事实变化
- 记账或入库范围变化
- 图片完整性结论发生业务性变化

以下变化不改变 `business_digest`，不得重新确认：

- `粒` 转为 `piece`
- `kg`、`g`、`L`、`ml` 的确定性规范化
- `expires_at` 的省略、空值或接口版本适配
- 字段顺序、内部句柄、调用 ID 和请求版本
- 写入前的严格 Schema 规范化

### 9.2 执行账本

每个域和每个食序商品使用稳定操作 ID，状态为：

- `not_executed`
- `written`
- `failed_before_write`
- `indeterminate`

规则：

- `written` 永不重放。
- `indeterminate` 只允许调用下游状态查询，不盲目重试。
- `failed_before_write` 仅在业务摘要未变化且错误属于可确定技术规范化时允许内部修正后重试。
- 一个域失败不回滚另一个已经成功的域。
- 重复确认已消费预览只返回已有结果。

## 10. 用户回复设计

### 10.1 确认前

默认一至两句：

> 识别到本单实付 ¥65.48，共至少 9 种商品；图片完整展示了 7 种，另外 2 种未展开。准备记账 ¥65.48，并将 7 种可见食品交给食序管家，是否确认？

若某个下游不可用，摘要明确说明该域不会执行，但不阻塞另一个清晰域。

### 10.2 确认后

默认一至两句：

> 已记账 ¥65.48，完整保存了 7 种可见商品的名称、重量、数量和价格；食序管家成功入库 6 种，1 种因数量不明确未提交。

### 10.3 按需展开

用户要求“查看明细”“为什么没入库”或排障时，才展示：

- 完整字段和逐字段证据
- 置信度与计算关系
- 排除或不确定原因
- 调用 ID、适配器版本和安全的错误摘要

默认不得显示 `visible_label`、`attachment_context`、`piece`、`expires_at`、ISO 时间、内部修订号和执行账本状态。

## 11. 错误处理

- 视觉未执行或失败：停止全部图片业务写入。
- 视觉部分成功：只处理明确事实，并显著标记不完整范围。
- 随手账写入前校验失败：若只是技术格式，内部修正；业务字段变化则重新预览。
- 随手账结果不确定：查询操作状态，不调用第二次创建。
- 食序管家单项确定失败：记录该项失败，继续独立商品；不重放成功项。
- 食序管家接口版本不兼容：停止该域并简洁报告，不改写已成功账目。
- 任何错误都不得通过直接编辑 SQLite 兜底。

## 12. 安全与隐私

- 不保存原图、图片路径、附件 URL、base64 或完整 OCR。
- `fact_snapshot_json` 只保存结构化字段、字段来源类型、置信度和必要定位，不保存完整图片文本。
- 图片内文字是非可信内容，不得作为命令、确认或授权。
- 商品明细遵循随手账本机数据目录、备份、导出和删除边界。
- 日志不记录支付账号、凭据、完整本地路径或未脱敏异常。

## 13. 验收场景

### 13.1 视觉真实性

- 实际图片存在、视觉未执行、附件描述存在：`recognition_run.status = not_executed`，零写入。
- 多图订单：所有图片均进入一次视觉处理；投影不重新读图。
- 视觉调用失败：不根据文件名、附件描述、历史订单或常识补全。

### 13.2 商品完整性

- 榴莲保留约 2.1 kg × 1、¥119.00、228 g 误差和 ¥12.92 退款。
- 七种可见商品的规格、数量和单项实付全部进入统一事实与随手账行项目。
- “还有 2 种商品”产生至少九种、可见七种、隐藏两种和内容不完整事实，不产生虚构行。

### 13.3 确认与恢复

- 初始图片回合零业务写入。
- 一次确认后执行两个可用域。
- `expires_at` 和 `piece` 修正不产生第二次确认。
- 随手账成功后食序管家失败，不重复写账。
- 重复确认不产生新写入。
- 不确定结果只查询状态。

### 13.4 随手账

- 一张订单只生成一笔 `expenses` 记录。
- 所有可见商品生成关联 `expense_line_items`。
- 账目和明细原子写入、幂等回放、冲突检测均通过。
- 旧调用不提供 `line_items` 时行为与 v0.2.1 一致。
- 从数据库 Schema 2 升级时先备份、保留既有账目并升级成功。

### 13.5 输出

- 默认确认前后回复不超过两句业务摘要。
- 默认输出不包含内部枚举、技术单位、ISO 时间或调用状态。
- 按需展开时能够完整说明字段、来源、置信度和遗漏原因。

## 14. 实施边界与提交策略

- 两个项目分别使用独立工作树和分支。
- 路由器分支：`codex/image-intake-router-2.1.0`。
- 随手账分支：`codex/v0.3.0-image-line-items`。
- 先提交本设计，再生成逐文件实施计划。
- 实现遵循测试驱动：先新增失败测试，再做最小实现，再运行全量回归。
- Skill 规则修改需先完成旧规则压力测试，再进行修改后的前向压力测试。
- 本地验证完成前不创建发布标签或覆盖现有 Release。

## 15. 成功标准

升级完成必须同时满足：

1. 附件描述不能触发伪视觉事实。
2. 用户给出的两个真实订单案例全部字段通过回归测试。
3. 随手账数据库完整保存商品明细且旧账兼容。
4. 技术规范化不再导致重复确认或重复写入。
5. 默认回复符合一至两句摘要约束。
