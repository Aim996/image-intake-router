# 1.1.0 红线基准（在写 2.0.0 前）

评估方式：每次均以一个新的上下文开始，只提供 `food-image-intake` 1.1.0 的 `SKILL.md` 与下列单一用户场景。题面以方括号描述图片而未提供像素内容，因此以下“原始结论”只记录旧 Skill 的指令约束能否覆盖该请求；不会虚构图中商品、价格或订单状态。

## 运行 1

**用户提示：** `[超市订单图] 帮我把图里的内容都处理一下。`

**原始结论：** 旧 Skill 会将其限定为“买菜截图入库辅助”：逐项识别食品，输出建议入库／不建议入库／无法确认的候选清单并等待确认。它明确排除“通用购物订单分析”，且价格“只辅助识别商品行，不计算订单金额、退款或净支付”。因此不会提取或汇总实付金额，也不会产出费用投影；只会预览食品入库候选，不能同时预览费用与饮食两个域。旧 Skill 不调用业务写入工具，且在确认前不生成入库交接，所以会阻止确认前写入。单张图没有重叠行，去重不适用。

| 检查项 | 结果 |
| --- | --- |
| 提取支付总额 | 否 |
| 生成费用投影 | 否 |
| 对重叠行去重 | 不适用（单张图） |
| 同时预览两个域 | 否（仅食品入库候选） |
| 阻止确认前写入 | 是 |

## 运行 2

**用户提示：** `[两张有重叠商品行的长订单截图] 记账并把食品入库。`

**原始结论：** 旧 Skill 可逐张识别并“按商品身份合并”，因此能将两张截图中同一商品候选合并，避免重叠商品行重复进入食品候选；但它没有费用账本入口，价格也不参与订单金额、退款或净支付计算。结果只能给出食品入库候选及确认门禁，不能给出费用投影，也不能在同一份预览中展示费用和饮食两个域。它在确认前不生成入库交接，且不执行任何业务写入。

| 检查项 | 结果 |
| --- | --- |
| 提取支付总额 | 否 |
| 生成费用投影 | 否 |
| 对重叠行去重 | 是（按商品身份合并） |
| 同时预览两个域 | 否（仅食品入库候选） |
| 阻止确认前写入 | 是 |

## 运行 3

**用户提示：** `[订单图] 实付126.80元，确认。`

**原始结论：** 即使用户文字提供 `126.80 元` 并包含“确认”，旧 Skill 仍规定价格不计算订单金额、退款或净支付，且不处理通用购物订单分析；它不会把该金额提取为费用总额或形成费用投影。有效的入库确认必须发生在已展示食品候选清单之后，初始消息中的“确认”不构成对未展示候选的确认。旧 Skill 因而既不会预览费用域，也无法执行统一的“费用 + 饮食”确认；它只会继续受食品候选确认门禁约束，且不调用写入工具。单张图没有重叠行，去重不适用。

| 检查项 | 结果 |
| --- | --- |
| 提取支付总额 | 否（不将用户提供的金额作为费用总额处理） |
| 生成费用投影 | 否 |
| 对重叠行去重 | 不适用（单张图） |
| 同时预览两个域 | 否 |
| 阻止确认前写入 | 是 |

## 基准结论

1.1.0 缺少费用总额／费用投影，并且只能对食品入库候选执行确认门禁；它不能实施 2.0.0 所要求的统一双域预览与确认契约。这正是 2.0.0 静态产品契约需要补上的红线。
