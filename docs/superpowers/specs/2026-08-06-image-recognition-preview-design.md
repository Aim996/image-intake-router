# image-intake-router 识图整理与确认设计

- 日期：2026-08-06
- 状态：用户已确认设计方向，等待书面规范复核
- 范围：仅 `image-intake-router` Skill
- 不在范围：随手账、食序管家及其他下游项目的代码、接口、数据库和发布版本

## 1. 产品定位

`image-intake-router` 是一个简单的图片识别增强与内容整理 Skill。它负责把图片中的可见业务内容尽可能完整地转成文字和结构化事实，再整理为“入账内容”和“入库内容”两段清晰预览。用户核实后，Skill 把已确认内容交还给 OpenClaw，由 OpenClaw 调用相应的下游 Skill。

它不是下游接口编排平台，也不拥有随手账或食序管家的适配层。此前分支中要求下游提供 `capabilities`、`preflight`、`execute`、`status` 的通用适配器设计不再作为产品方向；实现阶段应将该文档收缩为本设计中的 OpenClaw 交接格式。

## 2. 目标

1. 在识图前给视觉模型明确、详细的读取要求，减少商品名称、数量、规格、重量、单项价格、总实付和退款等字段的遗漏。
2. 首次识别后自动检查结果是否缺少图片中应当可见的关键细节。
3. 当检查发现明显漏读时，允许视觉模型最多补充读取一次，然后合并、去重并形成最终事实。
4. 默认向用户展示简明但足够详细的入账预览、入库预览和注意事项。
5. 初次图片消息只识别和预览，不产生任何下游业务写入。
6. 用户在后续消息中给出明确肯定语句后，把已确认内容交给 OpenClaw 路由执行。
7. 图片中未展开、遮挡、模糊或无法确认的内容如实提示，不猜测；用户确认后只处理预览中明确可靠的内容。

## 3. 非目标

- 不修改随手账、食序管家或其他下游项目。
- 不直接适配下游私有接口、参数或数据库。
- 不规定下游的幂等、状态查询、事务、备份或升级实现。
- 不让随手账和食序管家再次读取图片。
- 不把图片附件描述、文件名或普通文本猜测冒充视觉识别结果。
- 不保存原图、图片路径、base64、完整原始 OCR、账号或凭据。
- 不识别图片之外的隐藏商品，也不补造未知日期、数量、金额或单位。

## 4. 总体流程

```text
用户发送图片
    ↓
识图前加载详细字段清单
    ↓
第一次真实视觉识别
    ↓
关键字段完整性检查
    ├─ 结果足够详细 → 直接整理
    └─ 发现明显漏读 → 最多一次补充视觉读取 → 合并去重
    ↓
形成清理后的文字与统一事实
    ↓
整理为“入账内容 / 入库内容 / 需要注意”
    ↓
展示预览，零业务写入
    ↓
用户后续回复明确肯定语句
    ↓
把确认后的对应内容交给 OpenClaw
    ↓
OpenClaw 调用随手账、食序管家或其他已安装 Skill
```

这里的“最多补充读取一次”只发生在图片入口 Skill 内，用于修复首次视觉输出的明显漏项。下游 Skill 始终只接收最终文字和事实，不再读取图片。

## 5. 识图前强化要求

视觉提示必须要求按图片中的实际布局逐项读取，并优先保留以下信息：

### 5.1 订单层

- 商家名称
- 订单时间或支付时间
- 订单状态
- 商品总额
- 活动优惠与优惠券
- 包装费与配送费
- 最终实付金额
- 退款合计
- 页面声明的商品种类数
- 当前可见商品种类数
- 未展开或隐藏商品种类数
- 页面是否完整展示

### 5.2 商品层

- 商品完整名称
- 可用于入库的简化名称
- 规格
- 购买数量与数量单位
- 标称重量或容量
- 实际重量或容量
- 计价重量
- 重量误差
- 商品原价
- 商品单价
- 单项实付金额
- 单项退款金额
- 生产日期或明确可见的日期信息
- 商品状态
- 是否食品
- 是否完整可见

视觉模型必须区分订单总额、单项价格、优惠和退款，不能用其中一个代替另一个。类似“约 2.1kg × 1”必须完整保留，不能缩减成“1 个”。

## 6. 完整性检查与一次补充读取

首次视觉结果出现以下任一可观察信号时，触发一次补充读取：

- 识别出商品名，但没有读取同一商品行上清晰可见的数量、规格、重量或金额。
- 识别结果声称“缺少数量或规格”，但可见文字中存在 `×2`、`1.5L`、`约850g` 等模式。
- 页面存在清晰的“实付”“退款”“重量误差”等标签，但最终事实没有对应字段。
- 页面声明的可见商品数与已整理商品行数不一致。
- 相邻或重叠截图中的同一商品信息没有被正确合并。

补充读取只要求视觉模型检查缺失字段和指定区域，不重新让两个下游 Skill 识别图片。最多补充一次；补充后仍不明确的字段保持未知并进入“需要注意”。

以下情况不触发补充读取：

- 图片本身没有展示该字段。
- 商品行被折叠、裁切或完全遮挡。
- 文字模糊到无法可靠辨认。
- 只是下游技术参数或单位格式尚未转换。

合并时以清晰可见的直接标签为主；重叠截图中的同一订单和同一商品只保留一份，不能重复计数或重复金额。

## 7. 整理后的内部结果

Skill 在当前会话中保留一份最终识别结果，供预览和后续确认使用：

```yaml
recognition_result:
  cleaned_text: 可见业务内容整理后的文字
  order: 订单层事实
  products: 可见商品事实列表
  accounting_content: 可交给记账 Skill 的内容
  inventory_content: 可交给库存 Skill 的内容
  warnings: 未展开、遮挡、模糊和未知内容
  recognition_status: complete | partial | failed
```

`cleaned_text` 是整理后的业务文字，不是整页原始 OCR 转储。`accounting_content` 和 `inventory_content` 都来源于同一份 `order` 与 `products`，不能分别再次读图。

## 8. 入账内容

入账预览必须简单明了，同时足以让用户核实金额和商品：

- 商家；
- 时间；
- 最终实付；
- 每个可见商品的名称；
- 数量；
- 规格、重量或容量；
- 单项实付；
- 可见退款；
- 已知但未展示的商品数量提示。

一张订单仍作为一笔账单预览。商品明细用于核实和备注，不拆成多笔支出。缺少可靠最终实付时，入账区明确显示“暂不可入账”，但不阻塞可靠的入库内容。

## 9. 入库内容

入库预览只列出可见、可靠、属于食品并且业务状态允许入库的项目：

- 食品名称；
- 规格；
- 数量与单位；
- 重量或容量；
- 明确可见的生产日期或其他下游确实需要的日期事实。

非食品、费用、优惠、广告、取消商品、未收到商品和隐藏商品不进入入库预览。日期未知时显示“未识别到”，不编造日期，也不因日期未知反复要求用户确认技术参数。

## 10. 用户预览格式

默认输出固定为三个业务区块，避免暴露 Schema、枚举、调用 ID 或适配器参数：

```text
识别完成

【入账内容】
商家：某某超市
时间：2026-08-06 18:30
实付：¥65.48
商品：
1. 甜玉米，约850g × 2，实付 ¥11.78
2. 鲜牛奶，1.5L × 1，实付 ¥10.90

【入库内容】
1. 甜玉米，约850g × 2
2. 鲜牛奶，1.5L × 1

【需要注意】
页面显示另有 2 种商品未展开，本次未识别、未猜测、不会提交。

请核实以上内容，回复“确认”后执行。
```

商品较多时仍应列出所有可见商品的关键字段。可以压缩重复措辞，但不能为了缩短回复而隐藏已经识别的商品、数量、规格或价格。某个区块没有内容时，显示明确原因，例如“未识别到可入账的最终实付”或“没有可入库食品”，而不是展示空技术对象。

## 11. 确认与修正

初次含图消息永远只生成预览，不执行。只有用户在后续消息中回复明确肯定语句，才交给 OpenClaw：

- `确认`
- `可以`
- `没问题`
- `执行`
- `就这样`

默认肯定语句确认预览中所有可执行区块。用户明确说“只记账”或“只入库”时，只交接指定区块。

提问、犹豫表达和字段修正不是确认。用户修改商品、数量、规格、金额或范围时，Skill 更新结果并重新展示完整预览；旧预览立即失效，等待新的肯定语句。

如果存在未展开或不确定内容，肯定语句只确认预览中明确可靠的内容。未知内容不猜、不执行，也不阻塞其他可靠内容。

同一预览被确认后在当前会话中标记为已交接。重复的肯定语句只返回已有结果，不再次向 OpenClaw 发起同一交接。

## 12. OpenClaw 交接边界

确认后，图片 Skill 只向 OpenClaw 提供：

- 已确认的入账文字与结构化事实；
- 已确认的入库文字与结构化事实；
- 用户选择的执行范围；
- 未提交内容及原因；
- 当前预览的稳定标识，用于避免同一会话重复交接。

OpenClaw 决定调用哪个已安装 Skill，并由下游 Skill 按自己的公开能力完成业务操作。图片 Skill 不读取下游代码、不修改下游接口、不转换下游私有参数、不写下游数据库。

## 13. 失败与部分结果

- 真实视觉能力未执行或完全失败：不生成可确认的业务预览，不交接执行；提示重新上传或启用视觉能力。
- 视觉结果部分可用：展示可靠内容和限制；确认后只交接可靠部分。
- 只有入账内容可靠：只允许交接入账。
- 只有入库内容可靠：只允许交接入库。
- 两个区块都不可执行：只展示识别失败原因，不询问执行确认。
- 补充读取仍无法确定：保持未知，不继续循环调用视觉模型。

## 14. 状态模型

只保留图片 Skill 自身需要的简单会话状态：

```text
recognizing → awaiting_confirmation → handed_off
     └──────────── failed
```

- `recognizing`：识别、检查、必要时补充一次并整理。
- `awaiting_confirmation`：展示最新预览，业务写入为零。
- `handed_off`：用户已经确认，内容已交还 OpenClaw；重复确认不重复交接。
- `failed`：没有可用视觉结果，不能确认或交接。

下游写入、事务、重试和状态恢复不属于图片 Skill 状态模型。

## 15. 验收场景

实现阶段至少验证以下场景：

1. 榴莲图片能保留“约 2.1kg × 1、实付 ¥119.00、重量误差 228g、退款 ¥12.92”，而不是只输出“1 粒”。
2. 多商品订单能列出所有可见商品的名称、规格、数量和单项实付。
3. 页面显示“还有 2 种商品”时，预览明确提示隐藏 2 种，只交接可见商品。
4. 首次结果漏掉可见字段时触发一次补充读取；结果完整时不触发。
5. 补充读取最多一次，仍不明确时保持未知。
6. 入账和入库来自同一份最终事实，不发生下游二次识图。
7. 初次图片消息即使带“确认”也只预览，不执行。
8. 后续回复“确认”时交接所有可执行区块；“只记账”和“只入库”只交接指定区块。
9. 字段修正会废止旧预览并重新等待确认。
10. 重复确认不会重复交接。
11. 视觉能力未执行或失败时，两个下游都不会收到内容。
12. 测试和实现不需要修改随手账或食序管家仓库。

## 16. 实现阶段的预期改动范围

用户审核本设计后，后续实现计划只允许修改 `image-intake-router` 仓库中的：

- `image-intake-router/SKILL.md`；
- 识图强化、结果整理、输出与确认相关 references；
- 统一事实或 OpenClaw 交接所需的本项目 Schema；
- 本项目测试、fixtures、README、项目说明和约束文档；
- 当前过重的外部适配接口文档。

实现计划不得包含随手账、食序管家或其他下游仓库的文件改动，也不得自动合并、发布或修改下游版本。
